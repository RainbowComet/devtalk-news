Інженер із production-команди поділився результатами 18-місячного експерименту: компанія одночасно підтримувала два однакових сервіси — один на Spring Boot, інший на Node.js + Express — щоб зрозуміти, який стек краще поводиться в реальному продакшені.

Обидві системи працювали в однакових умовах:

* PostgreSQL
* Redis
* Docker
* AWS ECS
* однакові вимоги та навантаження
* по 4 інстанси на старті

На початку перевага була на боці Node.js:

Node.js (перші місяці):

* холодний старт ~800 мс
* ~120 МБ пам’яті
* Docker-образ ~180 МБ
* швидша розробка

Spring Boot:

* холодний старт ~3.2 с
* ~280 МБ пам’яті
* Docker-образ ~320 МБ
* повільніший старт команди

Перші результати виглядали очевидно: Node дешевший і легший.

Але ситуація змінилася після кількох місяців роботи.

⸻

Через 3–6 місяців почались проблеми з Node.js

За словами автора, Node-сервіси поступово збільшували споживання пам’яті:

120 МБ → 340 МБ → 500+ МБ → краш → рестарт

У підсумку команда витратила кілька тижнів на пошук memory leak, який знайшли в популярному npm-пакеті.

Рішення:

* ручне очищення
* власна обгортка
* новий технічний борг

Оцінка втрат часу: ~60 годин роботи інженерів

У той же час Spring Boot працював стабільно без помітних змін використання пам’яті.

⸻

Black Friday показав іншу картину

Під час 10× стрибка трафіку:

Node.js:

* масштабування до 40 інстансів
* ~850 МБ пам’яті на інстанс
* частина інстансів впала через OOM

Spring Boot:

* ~340 МБ пам’яті
* стабільна робота
* без падінь

Автор стверджує, що в цей момент “важкий Java-сервіс” споживав приблизно вдвічі менше пам’яті, ніж Node під навантаженням.

AWS-витрати за піковий період:

Node.js ≈ $1847
Spring Boot ≈ $923

⸻

Окрема проблема — залежності

Ще один фактор — підтримка пакетів.

За словами автора:

npm audit показав десятки вразливостей, а оновлення залежностей призвело до breaking changes та додаткових тижнів роботи.

Це сформувало додаткові витрати на підтримку.

⸻

Але є важливий нюанс

Цей кейс — досвід однієї команди, а не універсальне правило.

Результат сильно залежить від:

* архітектури сервісів
* якості коду
* бібліотек
* профілю навантаження
* досвіду команди

Існують великі системи на Node.js, які працюють роками без подібних проблем, так само як існують перевантажені та дорогі Java-моноліти.

⸻

Головний висновок

Історія ще раз показує, що:

“Легший стек” ≠ дешевший у продакшені

Реальна вартість технології формується не стартовими метриками, а роками підтримки, інцидентами, масштабуванням і стабільністю.
